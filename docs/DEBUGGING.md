# 从启动阶段黑屏到 HDMI 菜单

## 问题出现在哪个阶段

最初三系统都能从 rEFInd 启动，但内屏是唯一可见的启动输出。HDMI 外屏一直等到 Windows 接近锁屏时才亮，切换独显模式也没有自动解决。

因此排查集中在操作系统加载之前，而不是反复安装 Windows 显卡驱动。

## 逐步获得的证据

| 阶段 | 观察 | 能得出的结论 |
|---|---|---|
| 改 2560×1440 | rEFInd 闪屏，外屏没亮 | 单改分辨率没有选中外屏 |
| 故意设置不支持的 1×1 | 列出 1920×1080、640×480 等模式 | 这是当时接口的模式列表，不是全机所有接口的上限 |
| `connect -r` / `connect -c` | 外屏不亮，GOP 前后信息相同 | 通用连接没有改变当前输出 |
| 设备树与驱动检查 | NVIDIA UEFI 驱动存在；DP0 与 DFP3 两个子设备 | 不应继续简单归因为“没有显卡驱动” |
| 定向连接 DFP3 | 获得外屏 EDID Active、GOP、2560×1440 模式 | 驱动能够建立外屏图形输出 |
| 首次 6 秒色块 | 固件调用成功；只观察到背光/指示灯变化 | 返回成功还不能代替实际画面验证 |
| 三种模式各 15 秒 | 蓝、绿、红均实际可见 | HDMI 已证明可在 UEFI 阶段出图 |
| 独立 HDMI 菜单 | 菜单、按键选择与系统加载正常 | 显示切换可以与原版 rEFInd 配合 |
| 自动入口 | 接线开机、关机拔线后开机均正常 | 本机日常使用路径通过验证 |

第二轮色块测试同时改变了持续时间和模式切换顺序，不能把第一次没画面唯一归因于等待时间。

## 为什么两个 GOP 不一定是两块屏幕

本机初期的两个 GOP 实例使用同一个内屏 framebuffer，其中一个是控制台相关实例。只有把设备路径、EDID、framebuffer 及实际显示效果一起看，才能确定外屏是否真的活动。

同样，“有 EDID Discovered”只说明驱动发现了显示器信息；它与“该输出已经有活动 GOP”不是同一个状态。

## 程序的变化

- `target-output.c`：用已存在的设备路径定向连接，枚举模式并显示三种色块，随后尝试恢复内屏。
- `hdmi-menu.c`：切换到 1080p 后启动新的 rEFInd 实例，避免继续依赖切换前缓存的图形协议。
- `hdmi-auto.c`：把显示选择放到固件直接启动的入口，补上未接显示器、调用失败、日志不可写和菜单加载失败等处理。

主机测试共 25 个场景，但不模拟真正的 GPU、显示链路或厂商固件。它们只验证路径匹配、调用顺序、模式选择和返回分支。

## 后续机器怎样排查

1. 先确认原 rEFInd 和各系统能够独立工作。
2. 在 UEFI Shell 中查看 `drivers`、`devices`、`devtree -d` 及 GOP/EDID 协议。
3. 比较内外屏的设备路径，不要复制本机临时句柄编号。
4. 确认目标 ADR 节点实际存在，再考虑适配源码。
5. 先跑独立色块，再测菜单，最后才改变默认启动路径。

协议参考：[UEFI Console Support](https://uefi.org/specs/UEFI/2.11/12_Protocols_Console_Support.html)。固件对复杂显示拓扑的实际支持仍要以目标硬件验证为准。
